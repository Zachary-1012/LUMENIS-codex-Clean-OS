## 1. User problem and product invariant

- Role and authorized context: CTH Subject Context or BMP Brand/Market focus must arrive from an authenticated, server-authorized App context. The current AI-01 runtime ViewModel does not return either context, so this screen must show context as unbound and cannot submit a product-scoped task.
- User task: describe an analysis or draft task, inspect what real Evidence and recent AI executions are available, then start only when an authorized context and executable route are present.
- Completion signal: a real execution returns an execution ID; its response states whether Evidence was recorded. The current route does not return source-level Evidence IDs or a trace lookup route, so a recorded flag alone is not a completed source-level Trace.
- Owner and invariant: Shared AI / Agent Groups performs derived analysis within the caller's source-domain context. CTH owns commercial facts and Subject scope; BMP owns Brand/Market facts and focus. AI output remains a proposal and never replaces either domain's Canonical Data or Evidence.
- Out of scope: changing CTH/BMP ownership, generating fake AI output, inventing a context or trace API, or running write/export/publish operations from the intent composer.

## 2. Route, entry, exit and return

- Entry: AI-01 is mounted by the canonical App Shell and receives its shared Core client. The App can answer a configured Core Basic Auth challenge, but Product Core does not yet return a server-authorized Subject/Brand lens for this feature; product-scoped submission remains blocked.
- Read route: `GET /api/experience/screen/AI-01`; implementation `experience_runtime.py::screen_viewmodel` delegates to `_build_ai01()`.
- Intent route: `POST /api/experience/ai/intent`; implementation `experience_runtime.py::ai_intent` delegates granted work to `lumenis.shared.agents.skills.execution.run_execution_chain`.
- Exit: navigate to the originating product workflow only when the shell supplies a verified route. Gateway/catalog links in the existing backend aggregate are descriptive until navigation and caller context are verified.
- Trace / Return: the POST response exposes `execution_id` and `evidence_recorded`. No current AI execution detail / Evidence lineage GET callable was found. Preserve the response locally and show whether Evidence recording was confirmed; do not render a fabricated Evidence item or pretend that a source trace can be opened. Return restoration requires the shell to own prior Subject/Brand and navigation state.

### Exact callable contracts

- Screen read: `GET /api/experience/screen/AI-01`; JSON has `ok`, `screen`, `source`, `bound`, `sections`, `truth`, `binding`, and `generated_at`. It includes task suggestions, actual model-provider state, and the derivative-output rule. Unscoped Evidence statistics and execution history are not queried or serialized. Prototype fixture values are not used.
- Intent submit: `POST /api/experience/ai/intent` with `Content-Type: application/json`; `task` required and maximum 4000 chars. `action_type` defaults to `ANALYZE`; use no client-supplied actor ID, domain, product, skill, or raw context until the server provides a trusted caller-to-context contract.
- Authorization: `ai_intent()` uses SYSTEM `PermissionGate`; the isolated backend tests prove grant, pending approval, denied, permanent deny, unknown action and no execution on denied paths. Production `app.py::_basic_auth` protects API mutations when auth is enabled. The shared `LumenisCoreClient` supports in-memory Basic Auth after a Core 401, but authentication alone does not authorize a product lens. The screen currently exposes only the read aggregate and keeps submission disabled until server-trusted Subject/Brand context and its permission decision are available.
- Evidence: granted calls pass into the canonical Skill Execution chain, which attempts the Shared Evidence bridge. The route reports only whether evidence recording succeeded. There is no returned source-level trace object in this flow.
- Pagination/cancellation/idempotency: not exposed by this route. Do not imply cancellation, retry safety, or idempotency. A timeout after submit has an unknown execution outcome and must not trigger automatic resubmission.

## 10. Review decision and open questions

- Presentation decision: `DESIGN_READY` for the source-backed task-first composer, inspectable provider/Evidence/history areas, and honest unbound/blocked state after root review on 2026-09-24.
- Business decision: `BLOCKED` for end-to-end intent submission and source-level Evidence Trace. This presentation decision does not accept the AI business workflow or change any authorization boundary.
- Frontend-reviewable behavior: local task editing; safe, API-returned suggestions filling rather than executing the draft; real provider status; the compact unbound-context boundary; disabled submit with no request; and reversible inspector/disclosure behavior that preserves the draft.
- Still blocked: showing product-scoped Evidence/history without a trusted server-authorized Subject/Brand lens; submitting intent from the App without that context and Permission binding; and opening source-level Evidence Trace/Return. Do not show fabricated result rows, counts, context selectors, approval paths or success states.
- Product owner approved the overall App / UX plan and §§30–36 on 2026-09-20; this review does not reinterpret product semantics.
- Verified backend route and SYSTEM PermissionGate exist, so BACKEND-GAP-029 is not a missing-API finding. The AI-01 screen server now withholds whole-store Evidence statistics and unscoped execution history. BACKEND-GAP-030 has real provider aggregation in `_build_ai01()`; only model providers contribute to its provider health count.
- Blocking dependencies: (1) trusted current Subject/Brand lens propagation consumed server-side instead of trusting client `domain`/`user_id`; (2) an actor- and execution-scoped AI Evidence Trace lookup tied to `execution_id`; (3) distinguish empty execution query from database read failure. Basic Auth transport and App Shell routing are implemented; they do not satisfy these scope/trace requirements.
- Next action: resolve these at their existing auth/context/Shared Evidence owners, then enable the same composer and extend AI-01 acceptance. Do not create a new endpoint in this slice.
- Acceptance evidence required: Flutter widget tests for blocked submit, error/permission/Evidence states and responsive recomposition; existing backend permission tests; later authenticated live request and execution-to-Evidence Trace/Return E2E.
