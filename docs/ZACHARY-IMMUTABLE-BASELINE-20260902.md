# Zachary AI / ZBC Immutable Baseline — 2026-09-02

## Identity
1. Zachary AI is an independent, complete AI product and may ultimately become independently commercialized/productized.
2. Before independent launch, ZBC is Zachary AI's first cultivation environment, first real-use environment, and first business training environment.
3. Zachary operates within ZBC but is not owned by or structurally defined by ZBC.
4. ZBC remains an independent product/domain boundary.

## Bidirectional learning
ZBC → Zachary: approved ZBC data, cases, evidence, system knowledge and real-use results cultivate Zachary.

Zachary → ZBC: useful validated research, capabilities, reasoning improvements, product/UX improvements and engineering improvements may return through Evidence → Evaluation → Contract → Governance → Promotion.

Zachary general learning remains broader than ZBC. ZBC domain learning is restricted to ZBC-related knowledge, evidence, data and cases.

## Architecture invariants
1. ZBC remains independent and is not absorbed into the three-repository Zachary core.
2. DCC + SICI-Core + Research-Hub are the Zachary consolidation sources.
3. CTH-POMS remains the production/client-delivery priority inside ZBC; ZBMP remains a controlled enhancement layer rather than a second long-term independent codebase.
4. Subject type and content type remain distinct.
5. Existing core filtering/business rules must not be silently weakened by AI.

## Functional and governance invariants
1. Zachary remains complete; consolidation must not create a lightweight edition.
2. Mobile-first is the current delivery direction.
3. Shared capabilities require explicit ownership and Contract/Adapter boundaries.
4. Governance authorizes; Execution executes.
5. Baseline is authoritative; Supplements are additive and lifecycle-controlled.
6. Historical evidence remains auditable.
7. No PASS without executable evidence.

## Security invariants
1. No credentials, tokens, passwords or secrets in source-controlled documentation or frontend code.
2. Least privilege and explicit security gates are mandatory.
3. SICI RedNote/Xiaohongshu security boundaries remain unchanged.
4. Cross-repository changes must be bounded, reversible and auditable.

## Change rule
These identity, ownership, security and governance invariants cannot be changed by ordinary feature work. Any change requires explicit baseline-change evidence, impact analysis, migration/rollback planning and human approval.
