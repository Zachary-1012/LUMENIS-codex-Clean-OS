## 0. User problem and invariant

- User job: inspect whether the AI service layer has returned an available, not-ready or unavailable diagnostic state.
- This is diagnostic information only. It must not become a provider marketplace, model selection surface or business-success claim.
- AI-05 is not independently bound today. When the target returns `bound=false`, the bounded implementation may read AI-01's existing runtime observation and label it `fallbackDiagnostic`; it must not bypass 401/403 or other errors.
- The composition is a diagnostic topology plus returned observation series, not a KPI dashboard.

## 1. Routes and allowlist

- Primary read: `GET /api/experience/screen/AI-05`.
- Explicit fallback only when the primary response is valid `AI-05` with `bound=false`: `GET /api/experience/screen/AI-01` and parse its runtime/provider observation.
- Provider names are mapped to generic `local`, `optional`, or `generic` kinds. UI never shows raw provider/model names.
- Safe fields: generic state, bounded nonnegative latency, bounded returned call series and generated time. Missing values remain missing.

## 2. State and recovery

| State | Meaning | Action |
| --- | --- | --- |
| Loading | diagnostic read pending | Wait |
| Bound | AI-05 returned a valid diagnostic contract | Inspect returned state |
| Fallback diagnostic | only AI-01 observation is available | Inspect with explicit fallback label; do not claim AI-05 completion |
| Not ready / unavailable / unknown | returned service state | Show exact product-level state; no inference |
| 401 / 403 / offline / malformed | no trustworthy diagnostic | Retry or return; no fallback permission bypass |
