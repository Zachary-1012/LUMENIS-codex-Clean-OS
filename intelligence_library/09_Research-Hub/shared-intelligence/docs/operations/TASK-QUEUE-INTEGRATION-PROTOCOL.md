# 待执行任务队列整合协议 · V1

## 目的

当任一 AI 因额度、中断、环境或依赖原因未能执行任务时，任务不得丢失，也不得无限堆叠重复指令。恢复后必须以 GitHub 最新事实为准，对历史未执行任务与新任务进行去重、冲突检查、依赖排序和适配。

## 固定流程

```text
历史未执行任务
      +
新增任务 / 新 Evidence
      ↓
读取四库最新 SHA
      ↓
识别已完成 / 未完成 / 已被后续变更解决的任务
      ↓
去重
      ↓
冲突检查
      ↓
依赖排序
      ↓
最小执行队列
      ↓
执行 / 验证
      ↓
日志 → Commit → Push → Remote Verify
      ↓
NEXT FOR OTHER AI
```

## 状态规则

- `PENDING`：尚未执行。
- `IN_PROGRESS`：当前正在执行。
- `VERIFIED`：已有真实 Evidence 验证。
- `RESOLVED`：已被后续变更客观解决，不重复施工。
- `DEFERRED`：有明确原因暂缓，不能删除。
- `BLOCKED`：存在真实阻塞条件，必须记录阻塞原因。
- `NOT_VERIFIED`：做过动作但证据不足，不得当作完成。

## 整合原则

1. 新任务不能覆盖旧 Evidence。
2. 已经被解决的旧任务只标记 `RESOLVED`，不删除历史。
3. 相同目标的任务合并为一个执行单元。
4. 有依赖关系时先执行前置任务。
5. 发现冲突时停止冲突部分，进入 `BLOCKED`，不得强行施工。
6. 不为了清空队列而降低验证标准。
7. 不因为 AI 额度不足把任务标记为失败；保持 `PENDING` / `DEFERRED`。
8. 每次恢复工作必须重新读取当前四库事实，不能直接照搬旧队列。
9. 队列应追求最小复杂度：能合并就合并，能复用就适配复用，不能复用才新增。
10. 所有正式产品仍保持原职责边界，Hub 只承担研究、学习、证据、案例和能力登记协调，不成为生产运行时依赖。

## 双 AI 接力

豆包完成后留下 `NEXT FOR CHATGPT`；ChatGPT 完成后留下 `NEXT FOR DOUBAO`。对方读取后必须独立核验当前 SHA 和 Evidence，再决定是否执行。

**额度恢复后的第一动作不是盲目执行积压，而是“事实重建 + 队列整合”。**
