# Z-Brand Core

> **品牌传播与市场情报智能平台核心底座**
>
> 一个 Core、一个生产产品入口、一个受控增强能力层。
>
> - **CTH-POMS**：CorTech Lab · Guangzhou Taikoo Hui Public Opinion Monitoring System，当前主力生产/客户交付入口。
> - **ZBMP**：Z-Brand Monitoring Platform，Core 内的母平台增强能力层，通过受控 Feature Gate / License 等方式逐步启用，不作为第二套长期独立维护源码。
> - **Development-Command-Console（DCC）**：独立的内部 AI 研发中枢，负责审计、规划、受控升级和证据链，不是 CTH-POMS 的生产运行时依赖。
>
> **当前 GitHub 主线最新已进入 v5.8.9。** 本 README 以最新源码、提交记录、项目基线与已记录测试结果为依据；实时数据库、进程和运行环境仍必须以实际运行时检查为准。

## 1. 项目定位

本项目已经从单一的“舆情监测系统”演进为 **品牌传播与市场情报智能平台**。

核心目标不是只回答“有没有负面”，而是形成：

```text
品牌做了什么营销动作？
        ↓
谁在传播？
        ↓
产生了什么内容？
        ↓
形成了什么事件？
        ↓
事件如何演化、扩散、分化？
        ↓
对品牌意味着什么？
        ↓
风险 / 消费者需求 / 传播效果 / 竞品对标 / 决策输出
```

四层核心模型：

| 层 | 维度 | 核心内容 |
|---|---|---|
| 1 | **WHO** | 传播主体：KOS / KOL / KOC / 普通用户 / 媒体 / 官方 / 机构 |
| 2 | **WHAT** | 内容：UGC / 商业 / 官方 / 测评 / 体验 / 投诉 / 活动内容等 |
| 3 | **WHAT HAPPENED** | 事件：营销事件 / 传播事件 / 舆情事件 |
| 4 | **SO WHAT** | 品牌影响：传播贡献 / 情绪 / 风险 / 消费者需求 / 竞品 / AI 洞察 / 报告 |

### 核心业务约束

**主体类型与内容类型严格分离。**

- `subject_type=KOS`：账号/传播主体身份。
- `content_type=UGC`：具体内容属性。
- **禁止把 UGC 设计成账号类型。**
- KOL 可以发布 UGC；KOS 可以发布商业内容；同一主体可以产生不同内容类型。

## 6. 小红书采集：稳定优先

小红书是当前 PRIMARY 平台。目标是：

> **稳定、低风险、可解释、可恢复，而不是高频暴力采集。**

标准链路：

```text
稳定账号 / 合法登录态
 ↓
Persistent Browser Profile
 ↓
Playwright / CDP
 ↓
搜索 / 话题发现
 ↓
详情
 ↓
评论
 ↓
标准化
 ↓
质量检查
 ↓
主体过滤
 ↓
去重
 ↓
入库
 ↓
规则分析 / Ollama 增强
```

### 采集状态

生产层必须区分：

```text
SUCCESS
NO_NEW_DATA
RISK_WARNING
NEED_VERIFY
BLOCKED
SESSION_EXPIRED
COLLECT_ERROR
COOLING_DOWN
```

源码已有六态/更细状态时必须兼容，不得重复制造互相冲突的状态体系。

**任何失败、验证码、IP 风险、登录失效都不能显示成“0 条”。**

### Cookie / Session 失效机制

Cookie/session 在任何页面、任何任务、任何时刻失效，都进入**全局 Auth Recovery**，而不是简单跳转登录页。

系统内弹窗至少展示：

- 平台
- 账号
- 当前认证状态
- 失效/验证原因
- 合法二维码或平台正常登录/验证入口（当前流程支持时）
- “我已完成验证”
- “稍后处理”
- 当前暂停、冷却或恢复状态

完成人工合法验证后：

```text
验证完成
 ↓
CDP / Session 健康检查
 ↓
恢复任务
 ↓
小流量试探
 ↓
连续稳定后恢复正常调度
```

不得破解验证码、绕过安全验证或对抗平台风控。

### 300012 / IP 风险

```text
检测
 ↓
停止危险请求
 ↓
记录结构化状态
 ↓
熔断
 ↓
冷却
 ↓
健康检查
 ↓
合法人工验证（需要时）
 ↓
逐步恢复
```

熔断期间应拒绝新的采集启动请求，而不是继续撞平台。

```text
 ↓

```

## 9. 数据模型

### 基础数据关系

```text
客户
├─ 品牌（自有 / 竞品）
│  ├─ 监测配置
│  ├─ 传播主体库
│  ├─ 内容库
│  └─ 事件库
└─ 项目 / Campaign
```

### 传播主体六维画像

1. **身份**：KOS / KOL / KOC / 普通用户 / 媒体 / 官方 / 机构
2. **内容能力**：发文量、发布频率、爆款率、内容类型、垂直领域
3. **传播能力**：平均互动、互动率、传播速度、事件峰值贡献、扩散贡献度
4. **品牌关系**：官方 / 员工 / 合作 / 消费者 / 竞品 / 第三方
5. **舆情表现**：正负向、中性、风险等级、长期态度倾向
6. **事件贡献**：参与事件、贡献度、影响力权重

### 内容

内容字段与主体身份独立：

- `content_type=UGC`
- `content_type=COMMERCIAL`
- `content_type=OFFICIAL`
- `content_type=REVIEW`
- 体验、投诉、活动等可继续扩展

### 三类事件

- **营销事件**：品牌主动发起，例如周年庆、联名、快闪、Campaign。
- **传播事件**：市场/用户自发形成的热点。
- **舆情事件**：公众态度聚集，可正向也可负向。

事件不应成为孤立列表，通过 `event_relation` 表达：

- 触发
- 衍生
- 继发
- 并行

生命周期：

`发现 → 形成 → 增长 → 爆发 → 扩散 → 分化 → 衰减 → 结束`

目标关系：

```text
营销事件
   ↓
传播事件
   ↓
舆情事件
   ↓
品牌影响
```

## 10. 时间与数据质量

两个时间字段必须严格分离：

- `publish_datetime`：内容实际发布时间。
- `captured_at`：系统采集时间。

报告、日历和周期统计原则上按 `publish_datetime`。

相对时间如“小时前”“编辑于”等必须在采集解析层可靠归一化；无法可靠归一化时标记不确定状态，**不能拿采集时间冒充发布时间**。

数据质量至少关注：

- 平台原始 ID
- 标题 / 正文
- 作者
- 发布时间
- 原始链接
- 详情状态
- 评论状态
- 采集错误
- 风控/验证状态
- 主体归属
- 重复状态
- 部分采集状态

## 12. AI 架构：Ollama-first / 可退出 / Shadow Mode

### 正式生产原则

**本地 Ollama 是正式 AI Runtime。**

豆包、OpenAI 或其他云端大模型不得成为生产系统运行的硬依赖。历史外部 AI 代码在确认调用链后标记 Legacy/Optional，再决定清理。

即使所有 AI 都不可用，核心系统仍必须：

```text
采集
 ↓
主体过滤
 ↓
去重
 ↓
事件分析
 ↓
风险判断
 ↓
统计
 ↓
报告
```

正常运行。

### AI 可以增强

- 主体身份语义识别
- 内容类型分类
- 情绪解释
- 消费者需求提炼
- 事件聚类建议
- 事件关系建议
- 风险原因解释
- 评论总结
- 趋势解释
- 报告文字生成

### AI 不能独自决定

- 原始数据真实性
- 真实发布时间
- 广州太古汇主体最终口径
- 统计数量
- 报告周期
- 核心风险事实

### AI 审计链

```text
原始内容
 ↓

Ollama 输出

置信度 / 理由
 ↓
系统校验

人工修正（需要时）
 ↓

 ↓
```

- AI Shadow：AI 与系统原判断对照
- Evidence：研发过程证据链
- 多平台 Adapter：统一采集接口

这些能力应当服务于**研发、审计、分析和合法数据采集**，不得用于绕过平台安全机制。

## 14. 公网部署原则

系统可以通过公网提供访问，但生产边界必须安全：

```text
公网 HTTPS
 ↓
反向代理 / Cloudflare Tunnel
 ↓
认证层
 ↓
Web
 ↓
Worker / Scheduler
 ↓
数据库 / 本地 AI
```

- 不裸暴露 `8200`
- HTTPS 优先
- Cookie / Token / Secret 不进入 GitHub
- 生产数据库不得因远端更新被自动覆盖
- Web 与后台任务逐步解耦
- 公网发布前必须完成 Health Check、认证、关键页面和 API E2E

## 15. 数据安全

以下均属于数据资产：

- `.db / .sqlite / .sqlite3`
- ORM Model
- migration
- seed
- backup
- 导入/导出数据
- 原始采集数据
- 脱敏数据
- AI 样本

禁止：

- 未授权删除生产数据库
- 清空生产表
- 重建生产表覆盖数据
- 将 Cookie / Token / API Key / Secret 写入源码
- 将敏感凭证写入日志、前端或测试样例

数据库新增字段/表优先采用向后兼容迁移；任何迁移先备份并保留回滚路径。

## 16. 开发与发布门禁

一次升级只有同时满足以下条件才可称为完成：

1. 读取最新 GitHub HEAD。
2. 先审计影响范围，再施工。
3. 代码语法/导入检查通过。
4. 相关单测通过。
5. 数据库迁移检查通过。
6. 生产数据没有被删除或覆盖。
7. 蓝图 / API Smoke Test 通过。
8. 关键页面 E2E 通过。
9. 控制台 JS 错误扫描通过。
10. 主体口径回归通过。
11. 时间口径回归通过。
12. 采集异常状态可解释。
13. 新 Adapter 未误接管生产。
14. 无敏感凭据进入 Git。
15. 更新 CHANGELOG / PROJECT_STATUS / DEV_LOG。
16. 提供未完成项与回滚方式。
17. 完成后重新读取 HEAD 做二次核验。

标准流程：

```text
最新源码
 ↓
主基线
 ↓
影响范围分析
 ↓
最小补丁
 ↓
单测
 ↓
Smoke / E2E
 ↓
安全检查
 ↓
提交
 ↓
重新读取 HEAD
 ↓
发布结论
```

**真实 E2E 未完成，不得写“已完成”。**
