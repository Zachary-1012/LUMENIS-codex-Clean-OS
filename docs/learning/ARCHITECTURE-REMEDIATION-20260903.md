# ZBC 架构技术债｜建议处置方案（AI 学习产物）

> 生成：2026-09-03 智谱glm-4.5-air（架构重构项·只给建议不施工）

【项1】  
现状问题：app.py单文件6095行，Flask路由/UI/业务逻辑强耦合，维护成本高，测试困难。  
建议方案：按业务域拆分为微服务（如用户服务、数据服务），采用Flask Blueprint模块化路由层，UI层分离为独立前端项目，通过RESTful API交互。优先级P0（高），核心模块重构风险高，需分阶段灰度发布，影响全系统功能。验收标准：拆分后单文件不超过500行，模块间通过接口调用，CI/CD流水线覆盖各模块测试。  

【项2】  
现状问题：collector_automation.py采集逻辑与业务逻辑混合，策略变更易引发业务故障。  
建议方案：抽象采集策略接口（如ICollector），实现策略工厂模式，将采集配置外部化至JSON/YAML。优先级P1（中高），需梳理现有采集策略，迁移时可能短暂影响数据采集。影响范围：所有采集相关模块。验收标准：新增采集策略无需修改业务代码，配置热更新生效，单元测试覆盖策略切换逻辑。  

【项3】  
现状问题：intelligence.py AI推理与多模块直接耦合，缺乏统一接口，扩展困难。  
建议方案：设计AI服务网关，定义标准化推理接口（如/infer），支持多模型动态加载，内部通过适配器解耦具体实现。优先级P1（中高），需重构现有AI调用点，风险在于模型兼容性。影响范围：所有依赖AI推理的模块。验收标准：新增模型只需注册至网关即可被调用，性能监控覆盖AI服务，调用成功率≥99%。  

【项4】  
现状问题：database.py 51表直接SQL，业务逻辑与数据访问紧密耦合。  
建议方案：引入ORM框架（如SQLAlchemy），抽象Repository层，将SQL查询封装为领域方法，通过依赖注入注入业务层。优先级P0（高），需逐表迁移，可能引发数据不一致风险。影响范围：所有数据操作模块。验收标准：业务代码无直接SQL，Repository层单元测试覆盖率≥90%，事务隔离级别符合设计。  

【项5】  
现状问题：ai_resource_packs.py资源管理独立但缺统一接口，扩展困难。  
建议方案：定义资源管理接口（如IResourceManager），支持多类型资源（模型/数据集）的CRUD操作，实现插件化扩展机制。优先级P2（中），风险在于现有资源适配。影响范围：AI资源相关模块。验收标准：新增资源类型需实现接口，资源加载时间监控，内存泄漏检测通过。  

【项6】  
现状问题：xhs_cookie_bridge.py与xhs_cdp_collector.py认证与采集绑定具体平台，难复用。  
建议方案：抽象认证适配器接口（如IAuthAdapter），为不同平台实现适配器，采集器通过策略模式选择认证方式。优先级P2（中），需重构现有认证流程，风险在于平台兼容性。影响范围：多平台采集模块。验收标准：新增平台只需实现认证适配器，采集流程支持动态切换认证方式。  

【落地顺序建议】  
1. 优先处理database.py（P0）和app.py（P0），解决核心架构问题；  
2. 其次为collector_automation.py（P1）和intelligence.py（P1），解耦关键模块；  
3. 最后处理ai_resource_packs.py（P2）和认证模块（P2），完善扩展性。  
每阶段完成后进行全面测试，确保系统稳定性。
