## 一、先给结论

方案方向可行，但当前代码只完成了其中一部分，必须继续优化与闭环验证。

本方案基于最新 GitHub 源码核验，并结合 2026 年公开研究、Microsoft Entra Agent ID、OpenAI Agents SDK、智谱官方模型资料进行交叉验证。

核心判断：

- Evidence Chain、Runtime Contract、Agent Action Firewall、OBO/JIT、Checkpoint/Resume、Shadow/Replay/Canary、Contract-Centered Runtime 等方向均有现实技术依据。
- 研究成立不等于仓库已经实现；所有“已完成”必须以源码 + 测试 + 运行证据证明。
- 不能因为已有 Permission / Evidence / Gateway / Stability Monitor 就推断系统已经具备完整 Agent Runtime。
- 四仓继续保持独立：ZBC 是生产核心；OSAI 是智能能力核心；GGI 是独立 Growth Intelligence；LUMENIS Command 是独立研发控制台，不能成为前三者运行时依赖。
- 优化方向从“增加模块”升级为建立可验证运行时闭环：Intent → Permission → Action Firewall → Execution → Evidence → Evaluation → Recovery → Learning。

## 三、研究验证：哪些优化真的可行

### 1. Agent Action Firewall

工具暴露/Capability Gate 不等于真正授权。每次模型发起工具调用都应重新进行确定性、fail-closed 的参数级授权，并加入 scope、额度、幂等、default-deny。

LUMENIS 落地链：

`Intent → Tool → Parameters → Scope → Risk → Permission → Policy → Idempotency → Human Approval → Action → Evidence`

### 2. Runtime Safety Contract + Evidence

Agent 安全应成为 Runtime Contract，同时具备预防面和证据面：危险动作前阻断，任务完成前必须有可检查的测试、日志、diff、引用等证据。

因此“AI 说完成了”不能成为完成状态；必须由系统证据决定 `COMPLETED`。

### 3. Persistent Agent / Checkpoint / Resume

持久 Agent 可采用 Identity + Durable Memory + Versioned Body，并通过 quiesce → checkpoint → validate → bind → rehydrate → resume 实现恢复。

LUMENIS Runtime Guardian：

`Worker → Lease → Heartbeat → Checkpoint → Reaper → Retry → DLQ → Resume`

并定义 exactly-once / consume-once 约束。

### 4. OBO / Agent Identity

用户身份、Agent 身份、资源受众必须通过标准 OAuth/OBO 关系绑定。生产环境优先 managed identity / FIC / certificate，而不是长期 client secret。

LUMENIS 不自创伪 OBO：外部使用标准 OAuth/OBO；内部继续保留 task/run/step/action scope 与确定性授权。

### 5. Contract-Centered Runtime

Skill / Harness / Scaffold / Data Substrate 应契约化分离。LUMENIS 适合建立：

- Skill Contract
- Execution Contract
- Evidence Contract
- Permission Contract
- Lifecycle Contract

### 6. Shadow / Replay / Compare / Canary

先旁路观察，再历史重放，比较结果，再小流量 Canary，最后进入 Production。

该流程应成为模型、规则、Skill、Prompt、Schema 版本升级的默认发布路径。

## 四、关键发现：为什么必须优化

- EvidenceChain 当前允许的节点类型中不存在 `error`，失败分支不能继续写非法节点。
- InvocationResult 存在 `status` / `ok` 字段契约不一致。
- LocalEngine 捕获异常后可能返回空 content，存在“无异常但无结果”的假成功路径；必须明确 FAILED / DEGRADED / NO_PROVIDER。
- EvaluationSystem 不能以文件存在判断完整率/导出成功率。
- Provider 仍然过宽，死 Provider 会增加配置、测试、权限、故障路径和数据出境面。
- Subject SQL 与 Python 判断仍可能走不同 helper，造成页面、统计、报告、采集主体口径不一致。
- Repository Discovery 存在个人 Windows 路径，影响跨电脑、服务器、容器部署。

## 五、优化后的最终架构

核心运行链：

`Human → Intent → Task → Identity/Intent Binding → Skill → Action Firewall → Permission → Execution → Evidence → Evaluation → Decision → Outcome → Recovery → Learning`

四仓边界：

- **ZBC = Production Truth / Production Core**
- **OSAI = Intelligence / Capability Core**
- **GGI = 独立 Growth Intelligence**
- **LUMENIS Command = 独立 R&D Sidecar**

任何共享只能通过版本化 Contract / Artifact，不能通过运行时共享数据库、个人路径或隐式 import。

### 分层

| 层级 | 职责 |
|---|---|
| L0 Experience | Decision Workspace / NOW / WHY / NEXT / timeline |
| L1 Intelligence | Task / Research / Finding / Decision / Evaluation |
| L2 Capability | Skill Registry / Model Router / Tool Registry / Evidence |
| L3 Domain | CTH / ZBMP / GGI 等各自业务事实与数据真相 |
| L4 Foundation | Identity / Permission / Runtime / DB / Security / Recovery |

## 六、必须优化的 10 个工程闭环

### P0-01 主体口径统一

建立 SubjectPolicy / BrandProfile 单一真相；Python、SQL、采集、报告、统计全部由同一配置编译。

每次判断输出：`subject_id`、`policy_version`、`matched_words`、`excluded_words`、`reason`。

### P0-02 Invocation Contract

定义统一 `InvocationResult`：

`status / content / error / provider / model / evidence_id / evaluation_id / trace_id / duration_ms / degraded`

Engine、SkillInvoker、ZBC Adapter 全部只认这一 Contract。

### P0-03 Evidence Contract

业务证据链：

`Source → Evidence → Event → Case → Finding → Decision → Action → Outcome → Evaluation → Learning`

工程链继续保留：

`Task → Requirement → Skill → Agent → Action → File → Function → Data → Test → Result → Evidence → Decision → Commit → Lifecycle`

两条链通过 `task_id / trace_id / evidence_id` 关联，而不是混成一条字段杂乱的链。

Evidence persist 失败必须可观测，不能静默伪成功。

### P0-04 Action Firewall

所有产生副作用的 tool call 必须经过参数级授权。

禁止模型直接决定：`COMMIT / PUSH / DELETE / SEND`。

高风险动作必须 `HUMAN_APPROVAL`。

### P0-05 AI Gateway

逻辑 Provider 只保留：

1. **Zhipu Cloud**
2. **Local**

Local 内部可以使用 Ollama / LM Studio / llama.cpp。

删除 ARK / Qwen / OpenAI / DeepSeek 等死路径前，必须先全仓搜索 `import / env / config / fallback / tests / docs`。

Zhipu 模型不得继续依赖未验证或已失效的旧模型 ID；必须以当前官方有效模型为准。

Provider 失败必须显式返回 `FAILED / DEGRADED`，禁止通过空字符串让上层误判成功。

### P0-06 Runtime Guardian

实现：

`Worker / Lease / Heartbeat / Checkpoint / Reaper / Retry / DLQ / Resume / Crash Evidence`

所有恢复动作必须具备幂等键和 Resume Contract。

### P0-07 Evaluation 真证据

禁止“文件存在 = complete / export success”。

每个指标必须具备：

`Execution Evidence / Expected / Actual / Comparator / Score / Verdict / run_id`

### P0-08 Release Safety

统一发布链：

`Shadow → Replay → Compare → Canary → Production`

模型、Prompt、Skill、Rule、Schema 变更全部进入版本化发布门，并保留回滚能力。

### P1-09 Memory Lifecycle

Learning Asset 生命周期：

`RAW → Candidate → Validated → Generalizable → Admitted → Expired/Revoked`

每个 Learning Asset 必须带：`provenance / scope / version / validation / expiry / revoke`。

### P1-10 Impact Analysis

变更前自动追踪：

`File → Function → API → DB → Module → Contract → Product → Production Risk`

没有完成影响分析，不得直接进入生产。

## 七、AI 架构最终优化：智谱 + 本地

逻辑 Provider 只保留 `ZHIPU_CLOUD` 与 `LOCAL`。

### ZHIPU_CLOUD

用于复杂推理、研发、研究和需要云端能力的任务。模型 ID 不再硬编码旧模型，使用当前官方有效模型并通过运行时健康验证。

### LOCAL

统一承载 Ollama / LM Studio / llama.cpp。具体 Local runtime 可以变化，上层 Contract 不变化。

不允许继续形成：

`Zhipu → ARK → Qwen → OpenAI → DeepSeek → Local → ...`

Provider 越多，故障树、密钥面、数据出境面、测试矩阵和不可控行为越大。

AI 只负责候选分析、研究、生成、规划；生产事实由 ZBC Domain / Rule / Evidence 决定。

## 八、身份、OBO 与 Agent 安全

- `Human Identity (sub) ≠ Agent Identity (act) ≠ Task/Run/Step ≠ Resource`
- Token 必须绑定 `audience / resource / scope`。
- Token 与 `task_id / workflow_id / step_id / action_class` 建立 intent binding。
- 高风险写操作使用短生命周期、最小 scope、JIT credential。
- 生产环境优先 managed identity / FIC / certificate，而不是长期 client secret。
- 外部 OBO 使用标准 OAuth/OBO；内部 Action Firewall 再做一次确定性授权。
- 每次 Action 记录 `principal / actor / resource / scope / parameters_hash / policy_version / approval_id / idempotency_key / result / evidence`。

## 九、Runtime Guardian

目标不是承诺“永不崩”，而是把崩溃变成可检测、可恢复、可审计事件。

- **Worker / Lease**：任务具有唯一执行租约。
- **Heartbeat**：超过阈值标记 suspect。
- **Checkpoint**：保存可验证 continuation state。
- **Reaper**：回收过期 lease。
- **Retry**：按错误类型和幂等策略有限重试。
- **DLQ**：不可恢复任务进入死信，不循环打爆系统。
- **Resume**：从最后合法 checkpoint 恢复，防止并发重复消费。
- **Recovery Evidence**：每次恢复形成 Evidence，不允许恢复后直接伪装成正常成功。

Checkpoint 至少应能表达：

- Task State
- Execution State
- Authorization State
- Tool Effects
- Required Results
- Pending Effects
- Idempotency Keys
- Evidence References

所有 `send / write / update / delete / publish / commit / deploy` 类副作用都必须具备 `idempotency_key / effect_id / reservation_id / execution_id` 等可追踪机制。

## 十、评测体系最终升级

| 阶段 | 必须有 | 不能用 | 结果 |
|---|---|---|---|
| Execution | 真实执行记录 | 代码存在 | 执行确实发生 |
| Evidence | 日志/文件/diff/DB 等证据 | 模型口述 | 证据可回溯 |
| Expected/Actual | 期望与实际 | 单一分数 | 可解释 |
| Comparator | 确定性比较规则 | LLM 自评 | 可重复 |
| Verdict | PASS/WARN/FAIL/BLOCKED | 看起来不错 | 机器可判 |
| Regression | golden/badcase/历史回放 | 只跑一次 | 无关键回归 |

## 十一、最终验收标准

达到以下标准，才可以说“真的完成”：

- **主体**：同一输入在 Python、SQL、报告、统计、API 的主体判断一致，并有 `policy_version` 证据。
- **Skill**：ZBC → OSAI → Engine → Provider → Evidence → Evaluation 全链路可执行；成功、失败、阻断、降级四种状态可区分。
- **Evidence**：失败路径也能产生合法证据链；不允许非法 node type；证据持久化失败必须有明确状态。
- **AI**：只剩 Zhipu + Local 两条逻辑通道；全仓无死 Provider 的 import/env/fallback/test/doc 残留。
- **Evaluation**：所有关键指标均能回溯到真实 Execution/Evidence；不存在假设式 100%。
- **Security**：任何高影响 Action 都经过确定性授权；COMMIT/PUSH/DELETE/SEND 等默认 deny。
- **Recovery**：可模拟 SIGKILL、网络中断、Provider timeout、DB 锁、重复 resume，并证明不会产生重复副作用。
- **Release**：新版本先 Shadow/Replay/Compare，再 Canary，再 Production。
- **Independence**：四仓保持独立运行边界，不通过共享 DB、个人绝对路径、隐式 import 形成运行时耦合。
- **Portability**：Windows、本地 Linux、服务器、容器环境均通过 Repository Registry / Environment Contract 定位资源。

## 十四、最终判断

**可行，但不是现在已经完成。**

真正需要优化的不是继续增加更多 AI、更多 Provider、更多页面，而是把已经存在的 Skill、Permission、Evidence、Gateway、Evaluation、Runtime 组件收敛成一套统一、可验证、可恢复、可审计的 Runtime Contract。

最重要的工程判断：当前最先修的不是 UI，而是 Invocation Contract、Evidence Contract、AI Gateway 收敛、主体口径统一和真实 Evaluation。这些闭环完成后，再继续 Runtime Guardian、Memory、Shadow/Replay/Canary，整体架构才会真正进入可持续演进阶段。
