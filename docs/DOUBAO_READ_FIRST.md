## 二、当前项目定位

Z-Brand Core 是品牌传播与市场情报智能平台核心底座。

两条产品线：

- CTH-POMS：广州太古汇客户交付版
- ZBMP：多品牌品牌传播与市场情报母平台

目标是“一套 Core、两种 Release”，通过 Runtime Mode、Feature Flags、Brand Profile、权限和 Build/Release 配置实现差异，不长期复制两套核心源码。

## 三、当前 AI 原则

正式生产方向：**Ollama-first / Ollama-only Runtime**。

豆包、OpenAI 等云端模型不作为系统生命线。历史云 AI 代码先审计、标记 Legacy/Optional、默认关闭，确认没有运行依赖后再清理。

系统没有 AI 也必须正常完成：

`采集 → 主体过滤 → 去重 → 风险判断 → 事件分析 → 统计 → 报告`

AI 主要做增强：主体语义识别、内容分类、事件聚类建议、事件关系建议、消费者诉求、风险原因、摘要、趋势解释、报告润色等。

AI 输出必须可追溯、可人工修正，并支持 Shadow Mode 和样本回流。

## 四、小红书采集与登录恢复

小红书为当前主平台。采集目标是稳定、低风险、可恢复，不是高频暴力采集。

标准状态包括：

`SUCCESS / NO_NEW_DATA / RISK_WARNING / NEED_VERIFY / BLOCKED / SESSION_EXPIRED / COLLECT_ERROR / COOLING_DOWN`

出现验证码、300012、IP 风险、安全限制、登录失效时：

`识别 → 停止危险请求 → 记录 → 熔断 → 冷却 → 健康检查 → 合法人工验证 → 恢复`

不得破解验证码或绕过平台安全机制。

**重要产品要求：Cookie/session 失效不得简单跳转到登录页。** 全局 Auth 状态中心应在当前页面弹出系统内验证窗口，显示平台、账号、失效原因、平台正常流程提供的二维码/合法入口、人工完成验证按钮、稍后处理，以及当前任务暂停/恢复状态。验证完成后自动健康检查。

采集频率采用动态调度，不再把固定时刻和旧的“30/20 分钟、自动9次+手动3次”作为永久硬编码。

## 五、业务模型

四层模型：

`WHO 传播主体 → WHAT 内容 → WHAT HAPPENED 事件 → SO WHAT 品牌影响`

传播主体：KOS / KOL / KOC / 普通用户 / 媒体 / 官方 / 机构

内容：UGC / 商业 / 官方 / 测评 / 体验 / 投诉 / 活动等

事件：营销事件 / 传播事件 / 舆情事件

**subject_type 与 content_type 必须严格分开。** UGC 是内容属性，不是账号类型。

目标因果链：

`营销事件 → 传播事件 → 舆情事件 → 品牌影响`

事件关系使用 `event_relation` 等现有/规划结构表达触发、衍生、继发、并行等关系。

## 六、广州太古汇客户版保护规则

不得弱化或删除现有：

- `SUBJECT_WORDS`
- `SUBJECT_EXCLUDE_WORDS`
- `subject_hit()`
- `_subject_sql_and_values()`
- `aggregate_events()` 主体过滤
- `build_daily_report()` 主体过滤

广州太古汇必须与其他城市同名场景隔离。

## 七、数据保护

任何数据库、备份、迁移、SQL、seed、截图、报告和导入导出数据都是资产。

未经明确授权，不得删除、清空、重建或覆盖生产数据库。

新增字段/表优先采用向后兼容迁移。

Cookie、Session、Token、API Key、微信凭证不得进入 Git、源码、前端、日志或测试样例。

## 八、开发施工纪律

每次改动必须：

1. 先审计真实源码和依赖
2. 确认入口、调用链、数据库和蓝图
3. 选择最小兼容修改
4. 新能力优先旁路 / Shadow Mode
5. 做单测、接口测试和必要的浏览器 E2E
6. 检查数据库迁移和回滚风险
7. 更新 CHANGELOG / 开发日志
8. 给出真实测试结果，不得声称“已完成”而没有执行证据

**禁止为了“整洁”大规模重构稳定代码。**
