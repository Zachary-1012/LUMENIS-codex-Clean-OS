# AI Continuous Deep Learning & R&D Enhancement V1

## Purpose

Add continuous external research and self-repository learning to the existing R&D process without changing product definition, architecture, functionality, user roles, business boundaries, naming standards, safety gates, or canonical business truth.

## Daily minimum

Run at least 3 substantive research/learning cycles per day. A cycle is not a search-only action; it must include research, reading, understanding, comparison, extraction, evaluation, and a recorded decision. Reproduction/benchmarking should be used when practical.

Suggested coverage:
- Reasoning / planning / task decomposition
- Coding / code generation / debugging / repair
- Agent / tool use / context / long-horizon execution

## Research targets

Continuously study publicly verifiable methods from Doubao, Zhipu and other strong AI coding/reasoning/agent systems, plus relevant open-source projects, papers, and engineering practices. Do not treat unverified marketing claims as facts.

Study especially:
- complex requirement understanding
- task decomposition and intermediate plans
- repository understanding and code retrieval
- reuse-vs-create decisions
- code generation and modification
- test execution and error diagnosis
- automatic repair and multi-step execution
- context management and token efficiency
- tool use and convergence controls

## Self-repository learning

Each day also inspect the current production and intelligence repositories, recent commits, Canonical Data, Functions, Metrics, KOS, collection, reporting, visualization, AI, tests, CI/CD, lineage and observability. External learning must be evaluated against the actual codebase.

## Research-to-production rule

External method -> compatibility analysis -> architecture/security/performance/product-boundary review -> experiment -> benchmark/evaluation -> adaptation decision -> contract -> production validation.

Allowed outcomes: KEEP, ADAPT, MERGE, EXPERIMENT, REJECT. Never copy an external architecture merely because it appears advanced.

## Canonical integration

Learning must reinforce the existing canonical path: Canonical Data -> Canonical Function -> Canonical Metric -> Truth Surface/View Model -> UI/Report/Export/AI. AI must not become a competing source of truth, redefine production metrics, bypass permissions, safety gates, tests, or human approval boundaries.

## Capability assets

A repeatedly validated method should be converted into a reusable Skill, Pattern, Function, Tool, Test, Protocol, or Architecture Rule rather than remaining only as a note.

## Priority

P0: current production correctness, stability, security, and release-critical issues.
P1: coding agent, reasoning, repository understanding, testing, debugging, self-correction, tool use.
P2: frontier models, open-source projects, new tools and research.

P2 learning must never interrupt critical P0/P1 production work. Learning should run in parallel or in appropriate windows and feed the research/evaluation path.

## Required learning record

Record time, topic, research target, sources, findings, applicability, codebase relationship, experiment/evaluation result, adoption decision, affected capability, risk, and evidence.

## Long-term loop

Research -> Experiment -> Evaluation -> Adaptation -> Production -> Feedback -> Learning.

The goal is not to imitate any single model. The goal is to build the product's own governed reasoning, coding, tool-use, repository-understanding, evaluation, and capability-memory system while preserving production truth and architecture.
